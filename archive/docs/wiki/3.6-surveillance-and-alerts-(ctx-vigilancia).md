The `ctx-vigilancia` context is a core domain responsible for the operational lifecycle of alerts, notification deliveries, and escalations [docs/contextos/ctx-vigilancia.md1-14](https://github.com/pbaalerta-wq/hubp/blob/cc2edd14/docs/contextos/ctx-vigilancia.md?plain=1#L1-L14) It acts as the system of record for "what happened" after an incident is detected, tracking who acknowledged it, how many notifications were sent, and whether the situation escalated [docs/contextos/ctx-vigilancia.md5-9](https://github.com/pbaalerta-wq/hubp/blob/cc2edd14/docs/contextos/ctx-vigilancia.md?plain=1#L5-L9)

## 1. Domain Model and State Machine

The central aggregate is the `Alert`. Unlike raw sensor events, an `Alert` is a business record that references external evidence (e.g., a `sensor_event` or a `dwell_window`) [docs/contextos/ctx-vigilancia.md16-18](https://github.com/pbaalerta-wq/hubp/blob/cc2edd14/docs/contextos/ctx-vigilancia.md?plain=1#L16-L18)

### Alert State Machine

Alerts follow a strict, linear state machine to ensure accountability [docs/contextos/ctx-vigilancia.md133-134](https://github.com/pbaalerta-wq/hubp/blob/cc2edd14/docs/contextos/ctx-vigilancia.md?plain=1#L133-L134) Transitions are governed by the `AlertStatus` enum [crates/ctx-vigilancia/src/alertas/mod.rs36-41](https://github.com/pbaalerta-wq/hubp/blob/cc2edd14/crates/ctx-vigilancia/src/alertas/mod.rs#L36-L41)

|State|Description|Requirements|
|---|---|---|
|`Open`|Initial state when a rule is triggered.|Created via `AlertInput` [crates/ctx-vigilancia/src/alertas/mod.rs129-139](https://github.com/pbaalerta-wq/hubp/blob/cc2edd14/crates/ctx-vigilancia/src/alertas/mod.rs#L129-L139)|
|`Acknowledged`|A staff member has seen the alert.|Requires an `actor_id` and timestamp [docs/contextos/ctx-vigilancia.md135](https://github.com/pbaalerta-wq/hubp/blob/cc2edd14/docs/contextos/ctx-vigilancia.md?plain=1#L135-L135)|
|`Attending`|Staff is physically present or handling the resident.|Transitioned via `transition_alert` [crates/ctx-vigilancia/src/lib.rs109-120](https://github.com/pbaalerta-wq/hubp/blob/cc2edd14/crates/ctx-vigilancia/src/lib.rs#L109-L120)|
|`Resolved`|The incident is closed.|Terminal state [crates/ctx-vigilancia/src/alertas/mod.rs68](https://github.com/pbaalerta-wq/hubp/blob/cc2edd14/crates/ctx-vigilancia/src/alertas/mod.rs#L68-L68)|

**Transition Logic**: Valid transitions are restricted to `Open -> Acknowledged -> Attending -> Resolved` [crates/ctx-vigilancia/src/alertas/mod.rs63-70](https://github.com/pbaalerta-wq/hubp/blob/cc2edd14/crates/ctx-vigilancia/src/alertas/mod.rs#L63-L70) Any attempt to skip states or move backward results in an `InvalidTransition` error [crates/ctx-vigilancia/src/alertas/mod.rs10](https://github.com/pbaalerta-wq/hubp/blob/cc2edd14/crates/ctx-vigilancia/src/alertas/mod.rs#L10-L10)

## 2. Notification Delivery Lifecycle

Notifications are managed through an append-only model to preserve auditability. A retry does not update an existing record; it creates a new `NotificationDelivery` [docs/contextos/ctx-vigilancia.md41-42](https://github.com/pbaalerta-wq/hubp/blob/cc2edd14/docs/contextos/ctx-vigilancia.md?plain=1#L41-L42)

1. **Delivery Attempt**: Created with a `recipient_kind` (user, staff_group, or service) and a `channel` (push, tablet, sms) [crates/ctx-vigilancia/src/deliveries/mod.rs12-15](https://github.com/pbaalerta-wq/hubp/blob/cc2edd14/crates/ctx-vigilancia/src/deliveries/mod.rs#L12-L15)
2. **Delivery Events**: The outcome of an attempt is tracked via `NotificationDeliveryEvent`. Types include `sent`, `acknowledged`, and `failed` [crates/ctx-vigilancia/src/deliveries/mod.rs13](https://github.com/pbaalerta-wq/hubp/blob/cc2edd14/crates/ctx-vigilancia/src/deliveries/mod.rs#L13-L13)
3. **Summary**: The `DeliverySummary` provides a folded view of total sent, acknowledged, and failed attempts for a specific alert [crates/mana-app/src/vigilancia.rs70-75](https://github.com/pbaalerta-wq/hubp/blob/cc2edd14/crates/mana-app/src/vigilancia.rs#L70-L75)

**Sources**: [crates/ctx-vigilancia/src/lib.rs149-191](https://github.com/pbaalerta-wq/hubp/blob/cc2edd14/crates/ctx-vigilancia/src/lib.rs#L149-L191) [docs/contextos/ctx-vigilancia.md88-116](https://github.com/pbaalerta-wq/hubp/blob/cc2edd14/docs/contextos/ctx-vigilancia.md?plain=1#L88-L116)

## 3. Escalation Engine

Escalation is treated as a persistent state change rather than a transient side-effect [docs/contextos/ctx-vigilancia.md81-82](https://github.com/pbaalerta-wq/hubp/blob/cc2edd14/docs/contextos/ctx-vigilancia.md?plain=1#L81-L82)

- **Alert State**: The `Alert` struct tracks `escalation_level`, `escalated_at`, and `escalated_to` [crates/ctx-vigilancia/src/alertas/mod.rs156-158](https://github.com/pbaalerta-wq/hubp/blob/cc2edd14/crates/ctx-vigilancia/src/alertas/mod.rs#L156-L158)
- **History**: Every escalation event is recorded in the `alert_escalations` table, allowing for multiple escalation steps per policy [docs/contextos/ctx-vigilancia.md117-130](https://github.com/pbaalerta-wq/hubp/blob/cc2edd14/docs/contextos/ctx-vigilancia.md?plain=1#L117-L130)
- **Trigger**: The `escalate_alert` function updates the alert level and records the target in a single transaction [crates/ctx-vigilancia/src/lib.rs122-139](https://github.com/pbaalerta-wq/hubp/blob/cc2edd14/crates/ctx-vigilancia/src/lib.rs#L122-L139)

**Sources**: [crates/ctx-vigilancia/src/escalations/mod.rs1-19](https://github.com/pbaalerta-wq/hubp/blob/cc2edd14/crates/ctx-vigilancia/src/escalations/mod.rs#L1-L19) [docs/funcional/modelo-dominio/ctx-vigilancia.md63-73](https://github.com/pbaalerta-wq/hubp/blob/cc2edd14/docs/funcional/modelo-dominio/ctx-vigilancia.md?plain=1#L63-L73)

## 4. Data Flow: From Detection to Alert

Alerts are typically created by the `mana-sentinel` or `mana-engine` workers. To prevent "silent failures" where evidence is recorded but the alert fails, the system provides `create_alert_in_transaction` [crates/ctx-vigilancia/src/lib.rs37-42](https://github.com/pbaalerta-wq/hubp/blob/cc2edd14/crates/ctx-vigilancia/src/lib.rs#L37-L42)

## 5. HubClient and Workers

Workers (like `mana-sentinel`) interact with this context using the `HubClient` found in `mana-hub-client`. This client implements retry mechanisms for robust communication over the network.

- **Deduplication**: The engine uses `rules_alerted_since_in_transaction` to ensure an alert isn't re-triggered for the same "episode" (e.g., a resident remaining out of bed) even if the previous alert was resolved [crates/ctx-vigilancia/src/lib.rs53-65](https://github.com/pbaalerta-wq/hubp/blob/cc2edd14/crates/ctx-vigilancia/src/lib.rs#L53-L65)
- **Dwell Sweep**: Alerts can be generated by the passage of time (e.g., a resident staying too long in a bathroom). The `evaluate_due_dwell` logic is decoupled from the scheduler to allow for different execution models [docs/contextos/ctx-vigilancia.md192-195](https://github.com/pbaalerta-wq/hubp/blob/cc2edd14/docs/contextos/ctx-vigilancia.md?plain=1#L192-L195)
