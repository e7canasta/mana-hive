The `ctx-politica` context is a **core** domain module responsible for managing the lifecycle of alarm configurations for residents. It defines which rules are active, their clinical thresholds, and how these settings evolve over time through temporal versioning. It serves as the authoritative source for "Effective Policy" resolution, which the `mana-sentinel` and `mana-motores` components use to evaluate sensor data.

## Data Model and Temporal Versioning

Policy management in HubP relies on **temporal versioning**. Instead of updating a single row, every change to a resident's alarm configuration creates a new `AlarmProfileVersion`.

### AlarmProfileVersion Aggregate

The root aggregate `AlarmProfileVersion` tracks the configuration for a specific resident.

- **Immutability**: Once a version is created, it is never modified.
- **Validity**: The current configuration is identified by `valid_to IS NULL`. When a new configuration is applied, the previous one is "closed" by setting `valid_to` to the current timestamp within a database transaction [docs/funcional/modelo-dominio/ctx-politica.md38-44](https://github.com/pbaalerta-wq/hubp/blob/cc2edd14/docs/funcional/modelo-dominio/ctx-politica.md?plain=1#L38-L44)
- **Granularity**: Profiles are linked to a `ResidentId`, not a `BedId`. This ensures that if a resident moves rooms, their clinical alarm policy follows them [docs/contextos/ctx-politica.md87-88](https://github.com/pbaalerta-wq/hubp/blob/cc2edd14/docs/contextos/ctx-politica.md?plain=1#L87-L88)

|Field|Type|Description|
|---|---|---|
|`id`|`ProfileId`|Unique identifier for the version.|
|`resident_id`|`String`|Opaque reference to the resident.|
|`valid_from`|`Instante`|Start of the version's validity.|
|`valid_to`|`Option<Instante>`|End of validity (NULL if current).|
|`mobility_aid`|`MobilityAid`|Clinical aid (none, walker, etc.).|
|`autopilot`|`bool`|Whether the system automatically accepts recommendations.|
|`overrides_json`|`String`|Manual deviations from the selected template.|

## Alarm Catalog (TOML)

The `AlarmCatalog` is a **data-driven** configuration file (`config/alarm-catalog.toml`). It is not stored in the database but loaded at startup. This allows clinical thresholds to be adjusted via Git diffs without requiring code changes or database migrations [config/alarm-catalog.toml1-8](https://github.com/pbaalerta-wq/hubp/blob/cc2edd14/config/alarm-catalog.toml#L1-L8)

### Catalog Structure

1. **Groups**: Categorization of rules (e.g., `fall_prevention`, `sleep`) [config/alarm-catalog.toml44-62](https://github.com/pbaalerta-wq/hubp/blob/cc2edd14/config/alarm-catalog.toml#L44-L62)
2. **Rules**: Definitions of detectable events (e.g., `bed_exit`, `fall`).
    - `class`: Either `transition` (requires confirmation time) or `dwell` (requires tolerance time) [config/alarm-catalog.toml5-8](https://github.com/pbaalerta-wq/hubp/blob/cc2edd14/config/alarm-catalog.toml#L5-L8)
    - `locked`: If true, the rule cannot be disabled by any user override (e.g., the `fall` rule) [config/alarm-catalog.toml64-73](https://github.com/pbaalerta-wq/hubp/blob/cc2edd14/config/alarm-catalog.toml#L64-L73)
3. **Sensitivity Calibration**: Maps "low/standard/high" sensitivity to specific time factors and floor seconds to prevent alarm fatigue [config/alarm-catalog.toml25-36](https://github.com/pbaalerta-wq/hubp/blob/cc2edd14/config/alarm-catalog.toml#L25-L36)
4. **Presets & Templates**: Predefined configurations for specific risk profiles (e.g., `high_risk_falls`).

**Sources:** [config/alarm-catalog.toml1-200](https://github.com/pbaalerta-wq/hubp/blob/cc2edd14/config/alarm-catalog.toml#L1-L200) [docs/funcional/modelo-dominio/ctx-politica.md71-80](https://github.com/pbaalerta-wq/hubp/blob/cc2edd14/docs/funcional/modelo-dominio/ctx-politica.md?plain=1#L71-L80)

## Policy Resolution Hierarchy

The "Effective Policy" for a resident is calculated by merging layers of configuration. This resolution is handled by `mana-motores` but defined by the data in `ctx-politica`.

### Resolution Logic

The system resolves parameters in the following order of precedence:

1. **Catalog Preset**: The baseline defaults defined in the TOML.
2. **Resident Template**: The specific template assigned to the resident (e.g., "Cognitive Impaired").
3. **Manual Override**: Specific user-defined changes stored in `overrides_json` [docs/funcional/modelo-dominio/ctx-politica.md82-89](https://github.com/pbaalerta-wq/hubp/blob/cc2edd14/docs/funcional/modelo-dominio/ctx-politica.md?plain=1#L82-L89)

## Autopilot and Recommendations

HubP includes an "Autopilot" engine that suggests policy changes based on observed resident behavior (e.g., if a resident has many "near-miss" bed exits, it might recommend increasing sensitivity).

### Key Operations

- **Autopilot Mode**: If `autopilot` is enabled in the `AlarmProfileVersion`, recommendations can be applied automatically [docs/funcional/modelo-dominio/ctx-politica.md17](https://github.com/pbaalerta-wq/hubp/blob/cc2edd14/docs/funcional/modelo-dominio/ctx-politica.md?plain=1#L17-L17)
- **apply-recommendations**: A bulk operation (`POST /api/v1/alarm-presets/apply-recommendations`) that allows clinicians to approve system-generated suggestions for multiple residents at once [docs/contrato/modulos/politica.yaml144-170](https://github.com/pbaalerta-wq/hubp/blob/cc2edd14/docs/contrato/modulos/politica.yaml#L144-L170)
- **Observation Dependency**: Recommendations are derived from 14 days of observation summaries, though `ctx-politica` does not persist these raw summaries itself [docs/contextos/ctx-politica.md80-84](https://github.com/pbaalerta-wq/hubp/blob/cc2edd14/docs/contextos/ctx-politica.md?plain=1#L80-L84)

## Implementation Details

### Database Persistence

The context uses Diesel ORM with SQLite. The primary table is `alarm_profile_versions`.

```
-- Partial Unique Index ensures only one active profile per residentCREATE UNIQUE INDEX idx_resident_current_profile ON alarm_profile_versions (resident_id) WHERE valid_to IS NULL;
```
