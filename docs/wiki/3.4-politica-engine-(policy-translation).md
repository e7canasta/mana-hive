# Politica Engine (Policy Translation)

The **Politica Engine** serves as the translation layer between the high-level human-centric policies defined in the **Hub** (System of Record) and the low-level technical configurations required by the **Scene Engine** and **Sentinel Engine**. It acts as an Anti-Corruption Layer (ACL), transforming administrative intent (e.g., "Resident A is at high fall risk") into actionable technical parameters like hysteresis values, dwell times, and alert thresholds.

## Core Role and Data Flow

Politica bridges the gap between the "Natural Language Space" of care directives and the "Code Entity Space" of the processing engines. It observes policy changes and emits resolved calibrations that dictate how the system perceives and reacts to resident behavior.

### High-Level Translation Flow

1. **Input**: The engine observes `PolicyChangeDetected` events from the Hub.
2. **Resolution**: The `PolicyResolver` fetches the latest `ResidentPolicy`, `AlarmProfile`, and `SemanticBucket` definitions.
3. **Transformation**: The engine applies the **SceneCalibration DSL** to map semantic concepts to technical values (e.g., "High Risk" $\rightarrow$ `dwell: 2s`, `confidence: 0.9`).
4. **Output**: It emits `CalibrationChanged` events for the Scene Engine and `EffectiveRules` for the Sentinel Engine.

## Key Components

### PolicyChangeProcessor

The `PolicyChangeProcessor` is the primary entry point in the `politica-service`. It implements a reactive observer pattern, listening for signals that a resident's care plan or the facility's global configuration has changed. Upon detection, it orchestrates the re-calculation of the resident's active calibration.

### PolicyResolver

The `PolicyResolver` is the core logic unit within `politica-domain`. It performs a layered resolution of rules:

1. **Watch Level**: Determines the baseline monitoring intensity (e.g., "Standard", "Enhanced", "Critical").
2. **Level Template**: Loads default values for the determined Watch Level.
3. **Manual Adjustments**: Applies resident-specific overrides defined by clinicians.
4. **Time Windows**: Adjusts rules based on the time of day (e.g., stricter out-of-bed monitoring at night).

### EffectiveRules

The `EffectiveRules` object is the "Published Language" between Politica and the Sentinel Engine. It encapsulates everything the Sentinel needs to know to judge a `SceneFact`.

## SceneCalibration DSL

The Politica Engine translates clinical risk into the **SceneCalibration DSL**, which controls the sensitivity of the `SceneEngine`. This DSL manages the trade-off between detection speed and false-alarm prevention.

### DSL Parameters

- **Hysteresis**: Prevents "flapping" between states (e.g., rapidly switching between `IN_BED` and `SITTING_ON_EDGE`) by requiring a specific buffer.
- **Dwell**: The duration a resident must remain in a state before it is considered "stable" and a `SceneFact` is emitted.
- **Confidence**: The minimum probability threshold (from AI models) required to accept a state transition.
- **Heartbeat**: The frequency at which the system confirms the resident is still in the last known state.

### Alert Rules and Severity

Politica defines how the system reacts to specific `StateKind` triggers through `AlertRule` definitions.

## Domain Models: Resident Policy & Semantic Buckets

Politica uses several domain entities to organize policy logic:

- **ResidentPolicy**: The aggregate of all rules, schedules, and watch levels applied to a specific `ResidentId`.
- **AlarmProfile**: A reusable template of `AlertRule` sets (e.g., "Fall Risk Profile").
- **SemanticBucket**: A grouping mechanism used to categorize different types of behaviors or risks, allowing Politica to apply calibration logic to groups of similar events.
- **ClosureCondition**: Defines when an alert episode is considered finished.
    - `SAFE_ONLY`: The episode ends as soon as the resident returns to a safe state [platform/contracts/src/main/kotlin/com/manahive/contracts/policy/EffectiveRules.kt56](https://github.com/kerrvisiona-sudo/hive2/blob/f8142c8f/platform/contracts/src/main/kotlin/com/manahive/contracts/policy/EffectiveRules.kt#L56-L56)
    - `STAFF_AND_SAFE`: The episode requires both a staff presence detection AND the resident returning to a safe state [platform/contracts/src/main/kotlin/com/manahive/contracts/policy/EffectiveRules.kt57](https://github.com/kerrvisiona-sudo/hive2/blob/f8142c8f/platform/contracts/src/main/kotlin/com/manahive/contracts/policy/EffectiveRules.kt#L57-L57)

## Implementation Structure

Politica follows the standard engine tripartite structure:

1. **politica-domain**: Contains the pure logic for `PolicyResolver`, `EffectiveRules` generation, and the Calibration DSL. It has no dependencies on external infrastructure.
2. **politica-service**: The Spring Boot wrapper. It provides the `CalibrationProvider` port implementation, handles NATS JetStream subscriptions for policy changes, and manages the lifecycle of the engine.
3. **politica-batch**: A CLI tool used for offline policy testing. It allows developers to provide a set of Hub policies and verify the resulting `EffectiveRules` and `SceneCalibration` without a running environment.
