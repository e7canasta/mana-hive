Here is a thorough summary of what each engine contains and its role.

---

## Engines Overview

All three engines share an identical structure: a **pure-domain module** (no Spring, no framework dependencies -- just Kotlin data types and interfaces) and a **service module** (the Spring Boot imperative shell that wires messaging and runs the domain). They communicate over **NATS JetStream** with durable consumers, and depend on the shared `platform/domainKernel` and `platform/contracts` modules.

---

### 1. Scene Engine (`scene-engine`)

**Modules:** `scene-domain` + `scene-service`

**Role:** The "eyes" of the system. Converts raw sensor observations into credible, stateful facts about what each bed looks like right now.

| Source File | Purpose |
|---|---|
| `DigitalTwin.kt` | An immutable value object representing one bed's living model: its occupant, current `PersonState` (LYING, BED_EDGE, STANDING, ABSENT, UNKNOWN), how long it has been in that state (`stateSince`), and signal health of its monitor. No ORM, no setters -- it is a pure value. |
| `TransitionTable.kt` | A total finite-state machine table encoding which state-to-state transitions are legal and the minimum hysteresis duration each requires. An illegal transition is sensor noise and is discarded with an explanation. Ships with a `RELEASE_1` preset (e.g., LYING -> BED_EDGE needs 1500ms persistence). |
| `SceneInterpreter.kt` | The core `Engine` interface. Takes a `DigitalTwin` + one `Observation` and produces a `SceneVerdict` (updated twin + emitted `SceneFact`s). Handles: transition legality, hysteresis, per-state confidence thresholds, occupant binding from census snapshots, heartbeat/signal health, staff presence as facts, and explained discards. Explicitly does NOT decide alarms or measure dwells. |
| `ClockSweeper.kt` | A time-based patrol. Given all digital twins, it produces dwell-related facts (e.g., "has been at BED_EDGE for too long"). Dwells are derived state (`now - stateSince`), never persisted timers -- a restart cannot alter them. Handles dwell warnings (at a configurable ratio, default 80%), post-transition grace periods, post-presence rearm, and heartbeat watch. Uses `DwellMarks` for idempotency. |
| `SceneEngineApplication.kt` | The Spring shell. Consumes `perception.observation.v1.*` and `hub.census.snapshot.v1` from NATS; publishes `scene.fact.v1.<bed>`. Runs a 5-second sweep tick in-process (not cron). |
| `application.yml` | Connects to NATS at `localhost:4222`, durable consumer `scene-engine`, sweep interval 5s, heartbeat timeout 90s. |

### 2. Sentinel (`sentinel`)

**Modules:** `sentinel-domain` + `sentinel-service`

**Role:** The "brain" that decides whether a scene fact warrants bothering a human. The most expensive decision in the system.

| Source File | Purpose |
|---|---|
| `SentinelEvaluator.kt` | The core `Engine` interface. Takes a `SceneFact` + `EffectiveRules` (per-resident policy from the hub) + `EpisodeLedger` state and produces a `SentinelVerdict` containing `SentinelSignal`s and updated episode state. Handles: the episode algebra (open/close), ONE alert per (bed, rule, episode), suppression by staff presence with a record, the fatigue budget (INFO-level never interrupts -- it rolls into the digest), and escalation of `SIGNAL_LOST` as a technical alarm distinct from resident risk. |
| `EpisodeLedger.kt` | Decision state (not an aggregate) that is folded from scene facts. Contains: open episodes keyed by bed, each with an ID, origin state, and set of rules already alerted; and a `FatigueBudget` tracking interruptions this shift vs. a configurable max (default 12). When the budget is exceeded, new alerts become digest entries instead of live interruptions. |
| `SentinelApplication.kt` | The Spring shell. Consumes `scene.fact.v1.*` and `hub.policy.effective-rules.v1.*` from NATS; publishes `sentinel.signal.v1.<bed>` (incident/occurrence/suppression). Episode state is persisted locally and rebuilt from the scene stream on cold start. |
| `application.yml` | Connects to NATS at `localhost:4222`, durable consumer `sentinel`, max interruptions per shift: 12. |

---

### 3. Vigia (`vigia`)

**Modules:** `vigia-domain` + `vigia-service`

**Role:** The "voice" -- the delivery and escalation engine. Routes alerts to the right people through the right channels and manages their full lifecycle from raise to resolve.

| Source File | Purpose |
|---|---|
| `RoutingPlanner.kt` | The dispatcher `Engine` interface. Given an alert + a coverage snapshot (who is on duty, their role, ward, recent load) + a presence snapshot (who is physically in which room) + an escalation ladder, it produces a `DeliveryPlan` -- a non-empty list of `DeliveryStep`s, each specifying recipients, channel, timeout, and the reasoning. CRITICAL severity interrupts through every channel. The ladder always ends in a TERMINAL step so the alert can never silently die. |
| `AlertLifecycle.kt` | A pure event-sourced `Decider` (commands in, events out) implementing the full alert state machine. Phases: NONE -> RAISED -> ROUTED -> DELIVERED -> SEEN -> ACKNOWLEDGED -> SILENCED -> RESOLVED. Commands include: Raise, OrderDelivery, RecordDelivery, MarkSeen, Acknowledge, Escalate, Silence, ResolveByPresence, ResolveManually. Two invariants: one alert per `AlertKey`, and RESOLVED is absorbing (a resolved alert cannot be revived). |
| `VigiaApplication.kt` | The Spring shell. Consumes `sentinel.signal.v1.*` (IncidentDeclared) and `scene.fact.v1.*` (StaffPresenceDetected for loop closure); publishes `alarm.event.v1.<alert>`. Hosts the `AlertLifecycle` process -- escalation deadlines are derived from `DeliveryOrdered.occurredAt` and evaluated on sweep, so a restart never loses an escalation. |
| `application.yml` | Connects to NATS at `localhost:4222`, durable consumer `vigia`, delivery adapter: `console` (release 1). |

## How They Fit Together (Data Flow)

```
Sensors --> [Scene Engine] --scene facts--> [Sentinel] --signals--> [Vigia] --> Staff
                ^                                ^                      |
                |                                |                      |
                +--- hub.census (occupants) -----+--- staff presence --+
```

1. **Scene Engine** consumes raw observations, maintains a digital twin per bed, and emits scene facts (state changes, dwells, signal health, staff presence).
2. **Sentinel** consumes scene facts, evaluates them against per-resident rules, manages episode state (alarm fatigue budget), and emits signals (incident, occurrence, or suppression).
3. **Vigia** consumes signals, plans the full escalation ladder up front, and manages the alert lifecycle through delivery, acknowledgment, and resolution -- eventually reaching staff through the appropriate channel.
